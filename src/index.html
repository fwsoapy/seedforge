Accuracy & limitations
  • Structure placement is recomputed from Minecraft's own deterministic world-generation math. Nothing is looked up in a database, and nothing you type leaves your browser.
  • In 1.18 and later, a few structures (desert pyramids, jungle temples, woodland mansions) also depend on surface height. Cubiomes approximates that check, so rare false positives are possible.
  • "Estimated world spawn" can differ from the real in-game spawn by a few dozen blocks because the game's final spawn search depends on block-level terrain. Use "exact world spawn" for accuracy at a large speed cost.
  • Nether structure distances are measured in Nether coordinates from the Nether-side equivalent of your target point (x/8, z/8).
  • Village size is experimental. It buckets on the footprint of the village's starting meeting-point piece, which is real generation data, but the jigsaw expansion that decides the final size is not modelled. Village biome type and zombie villages are exact.
  • Biome criteria are sampled on a grid (1:16 for normal radii, coarser for very large ones), so a biome patch smaller than the sample spacing can be missed. A biome search never reports one that is not there, and is slower than a structure search.
  • Ravines and individual caves cannot be searched. They are carved into terrain per chunk rather than placed on a region grid, so Cubiomes does not model them. The lush caves and dripstone caves biome criteria are the closest available thing.
  • Proximity rules work within a dimension, and between the Overworld and the Nether - the Overworld side is divided by 8 and the rule is measured in Nether blocks. Rules reaching into the End are rejected, since End coordinates do not correspond to the other dimensions.
  • Stronghold filters cover position and ring only. What is inside a stronghold - portal room orientation, whether it has a library - comes from its piece layout, which Cubiomes does not generate.
  • Versions past the 1.21 Winter Drop come from a patch applied to Cubiomes at build time, since upstream has not been updated since November 2024.
  • Bedrock searching covers 1.18 and later, since that is when both editions moved to the same world generator. A Bedrock seed is a full 64-bit number like Java's: structure placement reads only its low 32 bits, biome generation reads all 64. Positions are computed with Bedrock's own generator and were diffed against a reference implementation across 10,530 cases; the biome side assumes the two editions still agree from 1.18 on. Villages, outposts, mansions, igloos and ruined portals have extra placement rules that can shift a result by a chunk, and world spawn is Java's estimate, so a Bedrock search targeted at spawn measures from the wrong point.
  • Telling a Bedrock fortress from a bastion is reverse engineering rather than a documented rule. The two share one region grid and the game builds one of them per site; the draw after the two that place it decides which, giving bastions two thirds of sites, which is the split the wiki reports. The rule matches two independent implementations, but both ship it disabled and it has not been confirmed in-game here. The site is exact either way, so a wrong call would name the wrong structure, never the wrong place.
  • Structure variant filters are Java only and are hidden when Bedrock is selected. Ruined portal type and placement, bastion type, zombie villages, igloo basements and cracked geodes all come from Java's RNG, so on Bedrock they would describe a different world. Village biome type still works, because it comes from biome generation.
  • "Double-check against the exact spawn" scans from the origin, which needs no spawn calculation and is around 270 times faster, then works out the real spawn of each match and requires the criteria to hold from there too. It is a filter on an origin search, not a faster way to run a spawn search: the radii still mean "from (0, 0)", with "and from the real spawn as well" added on top.
  • Always verify a seed in-game before committing a world to it.
